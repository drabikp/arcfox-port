## Problem Statement

The Motorola Razr 50 Ultra (Razr+ 2024, codename **arcfox**, Qualcomm SM8635 /
Snapdragon 8s Gen 3) has no LineageOS build. Stock Android on it carries more
telemetry and preinstalled Motorola/Google software than the owner is willing to
run. Two cheaper fixes were already tried and both failed:

- Debloating stock: "I tried to remove that but it always broke something else."
- Removing Google Play Services: "I tried to set free from Google Play Services
  but it wasn't stable."

The goal is not a working personal phone. **The owner already runs GrapheneOS on
a Pixel as their daily driver, and the Razr is sitting unused in a drawer.** The
goal is to produce a flashable, de-Googled LineageOS image that *other people*
can install on this device, which currently has no such option.

The question that opened the session was scoping, not design: "how much effort
would it actually be."

## What Makes This Cool

Three things, in ascending order of interest.

1. **A whole device class has no option.** Flip foldables are broadly unsupported
   by custom ROMs. The Razr 50 Ultra has an active enthusiast community, an
   unlockable bootloader, working TWRP, and nothing to flash onto it.

2. **The fold turned out to be configuration, not invention.** The working Razr
   40 Ultra port (`zeekr`) implements its entire foldable behavior in **four XML
   files**. `device_state_configuration.xml` declares CLOSED / HALF_OPENED /
   OPENED / REAR_DISPLAY off a `com.motorola.sensor.hall` "Flip Hall Effect
   Wakeup" sensor plus `android.sensor.hinge_angle` thresholds;
   `display_layout_configuration.xml` maps which physical display address is
   `defaultDisplay` in each state. That is AOSP's own DeviceStateManager. Google
   built the foldable framework into Android and the device tree only declares
   configuration against it.

3. **The build device is disposable.** The phone is a spare. It can be bricked
   and reflashed without consequence. Nearly everyone attempting ROM bringup is
   doing it on their only phone, which makes them cautious and slow. That
   constraint is absent here and it is worth more than any hardware spec.

## Constraints

- **Build machine:** 16-core desktop, 128GB RAM. Not a limiting factor. (A laptop
  with 25GB RAM was considered and rejected; it would have forced low `-j` values
  and thermal-throttled multi-hour builds.)
- **Experience:** No prior AOSP or ROM bringup. Prior Android work was app-level
  only (a Kotlin/Gradle patch to Linphone for Android). The instinct transfers;
  almost none of the specific knowledge does. Kernel, HALs, vendor blobs, SELinux
  policy, and a build system that takes an hour to report a failure are all new.
- **Device state:** Bootloader already unlocked. TWRP already flashed and booting.
- **Out of scope for v1:** VoLTE / VoWiFi. Explicitly listed as broken in any
  release post.
- **In scope for v1:** Working camera. This is the stated bar for a build worth
  putting in front of other people.

## Premises

All seven confirmed by the user, with premise 1 revised mid-session after the
GrapheneOS disclosure and premise 7 revised after the Codex cold read.

1. **(REVISED)** The goal is a flashable de-Googled LineageOS 23.x for arcfox
   with a working camera, built for other people. The owner's own de-Googling
   problem is already solved by GrapheneOS on a Pixel. This project is justified
   entirely by premise 5.
2. Not starting from scratch. Two independent Motorola SM8635/SM8650 kernel
   trees, an `sm8650-common` device tree, working TWRP, and a skeleton
   `lineage-23.0` arcfox tree all exist. This is bringup and completion.
3. The fold is configuration, using zeekr as a working reference.
4. The camera path is stock QTI camera HAL blobs plus LineageOS Aperture. The
   zeekr maintainer tried overriding Aperture with Motorola's MotCamera4 and
   reverted it. Genuine unknowns: the 50MP 2x telephoto, and the
   cover-display-as-viewfinder path.
5. There is an audience. Motorola's bootloader unlock program appears still
   operational. **Unverified for the specific SKU and region, and this is now
   the load-bearing premise of the whole project.**
6. Distribution is part of the design, not an afterthought.
7. **(REVISED)** Contact the two developers who stalled, but do not inherit their
   architecture. Build from the zeekr *shape*, keep the arcfox tree only for
   canonical identity and the extraction list.

### The gap

The arcfox `lineage-23.0` tree contains exactly three commits:

```
2025-12-02  arcfox: chmod +x
2025-12-01  arcfox: Add phone specs
2025-12-01  arcfox: Inital device configuration
```

Nine files. **No `fold/`, no `sepolicy/`, no `overlay-lineage/`, no `rootdir/`,
no audio/sensors/media configs.** zeekr has all of them.

Worse, and this is the finding that decided the approach:
`sm8650-common/BoardConfigCommon.mk` declares `TARGET_BOARD_PLATFORM := pineapple`
and **references no kernel at all**, and the repo has **no `lineage.dependencies`
file**. By contrast zeekr's `sm8475-common` declares four kernel repos explicitly
(`android_kernel_motorola_sm8475`, `-modules`, `-devicetrees`,
`android_hardware_motorola`). The Motorola-Pineapple common tree does not wire up
a kernel. It is a stub with a correct header comment.

Committers on the stalled tree: **Nikita Savchenko** and **pachadomenic**.
No public report of anyone booting LineageOS on arcfox exists.

### Corrections made during the session

Three claims were stated and then corrected against evidence. Recorded here so
they are not re-derived later.

- **Cover-display support is not framework work.** Initially claimed foldable
  support had "no upstream to inherit from." Reading zeekr's `fold/` directory
  disproved it. It is AOSP DeviceStateManager configuration.
- **The codename is `arcfox`, not `glory`.** A leak article named "Glory" as the
  presumed codename for XT-2453-3. The TWRP device tree README states plainly:
  "Device configuration for Motorola Razr 50 Ultra / Razr Plus (2024) (arcfox)."
- **The second rear camera is a 2x telephoto, not a periscope**, and the 32MP
  selfie is a hole-punch in the inner display, not under-display. The
  "periscope" wording came from the Motorola-Pineapple README; Motorola's own
  spec page says 2x. Both make the camera slightly easier than first stated.

## Approaches Considered

### Approach A: Hardware contract spike
**Effort:** S (one weekend) · **Risk:** Low
Do not build a ROM. Capture what the stock phone actually is, in all three hinge
states, and publish it as a blob-free public repo plus a zeekr-to-arcfox gap
checklist.
**Reuses:** zeekr's `fold/` XMLs as the target schema; the working TWRP tree for
recovery access.
**Pros:** Turns the project from archaeology into engineering. Publishable
artifact even if the project stops there. Gives a real opening to contact Nikita
and pachadomenic instead of a cold "why did you stop."
**Cons:** Produces no ROM and no boot screen.

### Approach B: Full bringup, zeekr-shaped
**Effort:** XL (months of evenings) · **Risk:** High
Fork zeekr's structure wholesale. Keep arcfox identity and
`proprietary-files.txt`. Pick the kernel by evidence rather than repo name. Wire
the kernel dependency that `sm8650-common` is missing. Target: boots, fold works,
camera works, VoLTE listed broken.
**Reuses:** zeekr's entire tree shape and fold config; both existing kernel
trees; TWRP for flashing and recovery.
**Pros:** It is the thing actually asked for. Real users at the end.
**Cons:** Unbounded long tail. Nobody has proven arcfox boots.

### Approach C: OpenFlip — the fold contract as the deliverable
**Effort:** XL+ · **Risk:** Med-High
The arcfox port becomes the vehicle; the artifact is a reusable
Motorola-foldable bringup template plus a fold test suite any future flip can run.
**Pros:** Changes who the user is, from other Razr owners to other porters, which
sidesteps the audience risk in premise 5. Genuinely upstreamable.
**Cons:** Ambition inflation on a device that has never booted. Doing C before A
produces a manifesto and no phone.

## Recommended Approach

**A now, B as the destination.** (User's choice, over the recommended
"A now, C as destination.")

Rationale: A costs one weekend and is the only approach that reveals whether B is
possible at all. It also tests premise 7 at near-zero cost. B rather than C is
the honest scope for a spare phone in a drawer: a working arcfox ROM, no upstream
framework ambition. C remains available later if the port succeeds and the fold
work turns out to generalize; nothing in A or B forecloses it.

The user chose the version that ships over the version that sounds better. That
is the correct call here and it should be respected in downstream planning: do
not let OpenFlip creep back in before arcfox boots.

## Open Questions

1. **Does Motorola's bootloader unlock program still cover this SKU and region?**
   This is premise 5 and it is load-bearing. If new owners cannot unlock, the
   audience shrinks to people who already did, and the project loses its
   justification. **Verify before investing months.**
2. **Why did Motorola-Pineapple stall after two days?** Ran out of interest, or
   hit a wall? Nikita Savchenko and pachadomenic can answer in one email.
3. **Which kernel tree is correct?** `Motorola-Pineapple/android_kernel_motorola_sm8650`
   or `Kendrenogen-moto-sm8635-6-6/android_kernel_motorola_sm8635`. The naming is
   ambiguous because SM8635 sits in Qualcomm's "pineapple" family alongside
   SM8650. Decide by evidence from the device (`ro.board.platform`, `uname -a`),
   not by repo name.
4. **Is the 2x telephoto exposed as an independent camera ID?** Determines whether
   Aperture can drive it or whether it needs HAL work.
5. **Does the cover display work as a camera viewfinder** under AOSP
   DeviceStateManager, or is that Motorola-proprietary? zeekr is the place to
   look first.
6. **Is anyone actually asking for this?** No specific human was named during the
   session who wants an arcfox LineageOS build. See "What I noticed" below.

on hosted CI runners (disk and time); expect local builds on the 128GB desktop
with manual release upload. Revisit only if the project reaches regular cadence.

**Note:** publishing device trees and configs is fine. **Do not publish extracted
vendor blobs**; keep the vendor tree local. That is both the legal norm and
standard practice in this ecosystem.

## Spike results (appended 2026-08-06, same session)

Approach A was executed immediately after this doc was approved, with the phone
in hand. Steps 2 and 3 of Next Steps are **done**. Full write-up lives in
`$HOME/workspace/motorola-lineageos/FINDINGS.md`; raw captures in
`contract/` (gitignored, carries the device serial).

It paid for itself. Two failure modes were found that no amount of reading
zeekr's repo would have surfaced:

1. **Display addresses are shifted by one between zeekr and arcfox.** arcfox is
   `...763` inner / `...764` outer; zeekr is `...762` inner / `...763` outer.
   Copying zeekr's `display_layout_configuration.xml` points `defaultDisplay` at
   a nonexistent address while disabling arcfox's inner screen. Silent
   black-screen boot with no log line naming an address.
2. **`hinge_posture` is quantized to a sparse ladder `{0, 70, 90, 110, 180}`**,
   verified by physical sweep, and a fast fold can skip rungs. Thresholds written
   against an assumed continuous angle can produce silently unreachable states.
   `HALF_OPENED_QVD` is reachable by exactly one value.

Also recovered: Motorola's own seven-state `device_state_configuration.xml`
pulled verbatim off `/vendor/etc/devicestate/`, giving real thresholds rather
than another phone's guesses.

Two open questions from below are now **answered**: the codename is confirmed
`arcfox` from `ro.product.device`, and `ro.board.platform` is `pineapple` (which
notably does *not* settle the kernel-tree question, since both candidate repos
are consistent with it).

One question got **harder**: there is no `display_layout_configuration.xml`
anywhere on the device and `mCurrentLayout` never changes when folding, so stock
routes the cover display through a proprietary layer. That file must be authored
from scratch with zeekr as the only reference, and zeekr's values are wrong here.
This, not camera, is now the top risk in the port.

**Step 4 (gap analysis) is also done**, and it answers Open Question 2. Both
`proprietary-files.txt` files in the Motorola-Pineapple trees contain exactly one
line: `# TODO: Bringup proprietary-files.txt`. zeekr's equivalents are 496 and
1177 lines. So no blobs were ever extracted, no bootable image was ever produced,
and the tree has no `fold/` directory at all.

**The December 2025 attempt did not hit a hardware wall. It stopped at
scaffolding, before bringup began.** That is good news for feasibility and it
changes the email: there is no black-screen hypothesis to lead with, because
they never got far enough to see one. Ask instead whether they intended to
continue and whether they'd hand over the repo or take a collaborator.

The full gap checklist, including the four fold files with arcfox's exact
`display_id_*.xml` filenames and a suggested work order, is in `FINDINGS.md`.

Steps 5 and 6 remain: publish `arcfox-fold-contract`, and send the email.
